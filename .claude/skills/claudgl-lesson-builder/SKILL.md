# ClaudGL Engine 강의 자료 제작 (A4 디자인 PDF)

강의 자료는 직접 레이아웃을 짠 A4 PDF 하나다. JLPT 강의 자료(`jlpt-lesson-builder`)의 디자인을 그대로 쓰고, 내용 부품만 엔진 개발용으로 바꿨다. 슬라이드나 Claude Docs 문서판은 만들지 않는다.

## 고정 정보

모든 경로는 저장소 루트(`D:\YunProject\ClaudGL_Engine`) 기준이다.

- 커리큘럼 (단일 원본): `Docs/Handouts/src/curriculum.py`
  - `PARTS` = Part 1〜5의 이름, `LATER_PARTS` = Part 6〜8(DX11·DX12·Vulkan), `LESSONS` = 강별 주제·핵심 개념·결과물·시간
  - `slug` = PDF 파일 이름에 들어갈 영문 주제, `ver` = 강의 자료 버전. 자료가 아직 없는 강은 `None`과 `0`.
  - `PLAN_VERSION`, `PLAN_DATE` = 계획서의 버전과 날짜
- 강의 계획서: `Docs/Handouts/src/plan.py` → `Docs/Handouts/ClaudGL_00_Plan_v<N>.pdf`
- 강 파일: `Docs/Handouts/src/lesson_<Part>_<순서>.py` → `Docs/Handouts/ClaudGL_<강 번호>_<slug>_v<N>.pdf` (예: `lesson_1_5.py` → `ClaudGL_1-5_Logger_v1.pdf`). 파일 이름은 `curriculum.handout_name("1-5")`가 만든다. 가장 최근 강 파일을 견본으로 쓴다.
- 빌드 엔진 `Docs/Handouts/_engine/`:
  - `common.py` — 헬퍼와 build(). 강 파일이 `from common import *`로 쓴다.
  - `base.css` — 스타일 (색·글꼴은 맨 위 `:root` 변수)
  - `render.py` — 설치된 Chrome/Edge를 headless로 돌려 HTML → A4 PDF. 쪽 번호와 꼬리말은 CSS `@page` 여백 상자로 넣는다 (Paged.js·Playwright 없음).
  - `sheet.py` — 검수용 접촉 인화와 쪽 확대
- 부품 견본: `Docs/Handouts/src/gallery.py` → `_build/gallery.pdf`. 엔진을 고친 뒤에는 이것부터 다시 빌드해 깨진 곳이 없는지 본다.
- 중간 산출물: `Docs/Handouts/_build/` (HTML, 접촉 인화). `.venv/`와 함께 `.gitignore`에 들어 있다.
- 빌드 환경: `Docs/Handouts/.venv` (pygments, pymupdf, pillow). 없으면 만든다.
  `python -m venv Docs\Handouts\.venv` 다음 `Docs\Handouts\.venv\Scripts\python.exe -m pip install pygments pymupdf pillow`
- 글꼴은 PC에 설치된 것을 쓴다: 본문 Noto Sans KR, 코드 D2Coding, 표지 큰 글자 Cascadia Code.

## 번호와 버전

Claud가 2026-11-14에 정한 규칙이다 ("강의별로 넘버링 제대로 해 줘. 1-1, 1-2 이런 식으로", "새 버전 나올 때는 v1 v2 v3 이런 식으로 붙여 줘").

- 강 번호는 `Part-순서`다: `1-1`, `1-2`, … `5-4`. 본문에서는 "1-5강"이라고 쓴다. "N과", "Part A", "복습 N" 같은 예전 표기는 쓰지 않는다. 번호는 `LESSONS`의 순서에서 자동으로 매겨지므로, 강을 끼워 넣으면 같은 Part의 뒤 번호가 밀린다. 그때는 `plan.py`와 강 파일 본문의 "N-M강" 참조를 전부 다시 맞춘다.
- 자료 안의 장·절은 점으로 잇는다 ("3장", "3.2절"). 강 번호와 섞이지 않게 강에는 늘 "강"을 붙인다.
- 모든 PDF 이름은 `_v<N>`으로 끝난다. 표지 눈썹과 꼬리말에도 버전을 적는다.
  - 만드는 도중(검수하며 다시 빌드)에는 같은 버전 파일을 덮어쓴다.
  - Claud에게 한 번 건넨 PDF는 덮어쓰지 않는다. 그 뒤에 고치면 버전을 올린다: 강의 자료는 `curriculum.py`의 그 강 `ver`, 계획서는 `PLAN_VERSION`(과 `PLAN_DATE`). 예전 버전 파일은 지우지 않고 둔다.
  - 빌드가 "is open in a viewer"로 멈추면 그 버전은 이미 건넨 것이다. 버전을 올리고 다시 빌드한다.

## 공통 규칙

- **멘토 원칙이 최우선이다.** 프로젝트 `CLAUDE.md`대로 Claud가 모든 엔진 코드를 직접 쓴다. 강의 자료에 완성된 구현을 싣지 않는다. `code()`는 다음 용도로만 쓴다.
  - `tag="now"` 현재 코드 — 저장소에 실제로 있는 코드의 인용
  - `tag="sketch"` 선언 스케치 — 클래스·함수의 모양만. 본문 없음. 주석은 답이 아니라 질문으로 단다.
  - `tag="usage"` 사용 예 — 완성되면 부르는 쪽이 어떻게 보이는지
  - `tag="syntax"` 문법 — 처음 보는 API·C++ 기능의 호출 형태 1〜3줄
  - `tag="bad"` 안티패턴 — 왜 곤란한지 보여 주는 짧은 예
  - 설계에서 갈리는 지점은 선택지와 장단점 표로 보여 주고 `box("decide", …)`로 Claud에게 남긴다. 고르지 않는다.
  - 해설 장에는 질문의 답과 근거만 쓴다. 미션의 완성 코드는 Claud가 명시적으로 요청할 때만 채팅으로 준다.
- 코드 안 주석은 영어만 쓴다. build()가 코드 블록의 한글을 `issues`로 잡는다.
- 문체: 본문은 한다체("~다", "~한다"). 미션·질문의 지시는 하시오체("답하시오"). 채팅 답변은 사용자 `CLAUDE.md`를 따른다 (표는 영문만 쓰고 아래에 한글 설명, 리눅스 명령어에는 해설).
- 정확성: 현재 코드를 말할 때는 그 파일을 실제로 읽고 `파일:줄 번호`로 적는다. 기억이나 `CLAUDE.md`의 설명만으로 쓰지 않는다. 읽은 날짜를 본문에 적는다. API 동작은 확실한 것만 단정하고, 버전에 따라 다른 것은 버전을 적는다.
- 순서 지키기: 앞 강에서 만들지 않은 것을 전제로 삼지 않는다 (예: 1-5강 전에는 로그 매크로를 쓴 예시를 넣지 않는다). Part 2는 일부러 추상화하지 않는 구간이므로 클래스로 감싸는 방향을 안내하지 않는다.
- 연결: 개념 장마다 `box("ue", …)`(UE5에서 같은 자리에 있는 것)와 `box("cs", …)`(닿는 전공 주제)를 붙일 수 있으면 붙인다. Claud는 UE5 실무자이고 전공서로 CS 구멍을 메우는 중이다. API마다 달라지는 점은 `box("api", …)`. 음악 비유는 자연스러울 때 한두 개.
- 칭찬으로 채우지 않는다. 현재 코드의 문제는 위치와 증상으로 담담하게 적는다.
- C++ 프로젝트를 컴파일하지 않는다. 커밋은 요청받았을 때만 한다.

## 내용 구성

1. 표지 — `cover(눈썹, 큰 식별자, 강 이름, 부제, 정보 표, note, toc)`. 큰 식별자는 그 강의 핵심 클래스·함수 이름(`Raw('G<span class="ac">Logger</span>')`처럼 일부를 강조). 정보 표 = 목표 결과물 / 핵심 개념 / 선수 지식 / 예상 시간 / 건드릴 파일. 눈썹은 `CLAUDGL ENGINE · PART 1 · 1-5 · v1`.
2. 왜 필요한가 — 이 강이 없으면 무엇이 불편한지. 지금 코드에서 그 불편이 드러나는 줄(`tag="now"`).
3. 개념 장 3〜5개 — 소절, 그림(`flow`·`layers`·`iface`), 비교 표, 상자, 맞는 것·틀린 것은 `ox()`
4. 설계 — 선언 스케치, 파일 배치(`tree`), 선택지 표 + `box("decide")`
5. 구현 미션 — `steps()`. 단계마다 힌트를 가벼운 것 → 구체적인 것 순으로. 힌트는 방향이지 코드가 아니다.
6. 흔한 함정 — 표: 증상 | 원인 | 확인 방법
7. 완료 기준 — `checklist()` + 화면·로그에 나와야 할 결과(`console`). 검색으로 확인되는 조건을 하나 넣는다.
8. 생각해 볼 질문 — `exgroup` + `qlist`, 코드를 쓰지 않고 답하는 질문 4〜6개
9. 해설 — `answers()`, 답과 근거 한 줄씩
10. 용어집 — `glossary_chapter(n, [(용어, 원어·식별자, 뜻)])`

## 코드가 먼저 있는 강 (이미 만든 코드를 다시 읽는 자료)

1-1 〜 1-3강은 Claud가 코드를 먼저 쓰고 자료가 나중에 나왔다. 이런 강의 자료는 미션 대신 저장소의 코드를 인용해서 읽는다. Claud가 "지난 것 복습하게 자료로 뽑아 줘"라고 할 때도 이 양식으로 그 강의 자료를 만든다. 번호는 다른 강과 똑같이 `Part-순서`다. 견본은 `lesson_1_3.py`.

- 이미 Claud가 쓴 코드이므로 `tag="now"`로 그대로 인용한다. `start=<실제 줄 번호>`를 줘서 줄 번호를 표시하고, 본문은 그 번호로 설명한다. 인용은 글자 하나 바꾸지 않는다 (`r"""…"""` raw 문자열).
- 구성: 표지(정보 표 = 다루는 범위 / 핵심 개념 / 관련 파일 / 읽는 시간 / 코드 기준 커밋과 읽은 날짜) → 한 장으로 보기(그림) → 개념 장(인용 코드 + 줄별 표 + 상자) → 다시 보면 걸리는 곳(위치 | 관찰 | 이어지는 강) → 스스로 설명해 보기(질문 6개) → 해설 → 용어집.
- 미션은 없다. "다시 보면 걸리는 곳"에는 관찰만 적고 고치는 방법은 적지 않는다. 고치는 일은 이어지는 강의 미션이다.
- 확인하지 않은 것은 확인하지 않았다고 쓴다 (예: "빌드해서 확인하지는 않았다").
- 코드가 바뀐 뒤 다시 만들 때는 `curriculum.py`의 `CODE_COMMIT`과 `CODE_READ_DATE`를 고치고 모든 줄 번호를 다시 맞춘다. 버전도 올린다.
- 장은 이어 흐르게 두고, "다시 보면 걸리는 곳"과 "스스로 설명해 보기"만 `pb=True`.

## 순서

1. `curriculum.py`에서 그 강의 행(주제, 핵심 개념, 결과물, 시간)과 앞뒤 강을 읽는다. 계획서 PDF의 해당 Part 장에 적힌 "결정할 것"도 확인한다.
2. 그 강이 건드릴 엔진 파일을 전부 읽는다. 현재 상태·문제 위치를 `파일:줄`로 메모한다. 앞 강의 완료 기준이 실제로 충족됐는지도 본다. 안 됐으면 자료를 만들기 전에 Claud에게 알린다.
3. `curriculum.py`에서 그 강의 `slug`를 정하고 `ver=1`로 둔다. `lesson_<Part>_<순서>.py`를 쓴다. 내용만 쓴다: `COVER`, `ch1`…, 맨 아래 `build()` + `render()`. 머리 부분(경로 설정, import)은 최근 강 파일과 같다. 강 제목·번호·버전은 `ME = lesson("1-5")`에서, 출력 경로는 `handout_name(ME["id"])`에서 가져온다.
    - 텍스트 인자는 자동으로 이스케이프되고 인라인 표기를 받는다: `` `코드` ``, `**굵게**`, `==강조==`. C++의 `<`, `>`를 그대로 써도 된다. HTML을 직접 넣을 때만 `Raw(...)`.
    - 헬퍼: `chapter(n, title, body, lead, pb, side)`(제목·도입문·첫 블록을 한 덩어리로 묶음), `h3(num, t)`, `h4`, `p`, `ul`, `ol`, `table(cols%, header, rows, cell_cls, sum_row, compact)`(rows에 `Group("제목")`을 넣으면 묶음 제목 줄), `box(kind, title, body)`(point / why / ue / cs / api / warn / hint / decide / dark, title이 None이면 기본 이름), `cards`, `ox(good, bad)`, `code(src, lang, title, tag, hl, start)`(`start`를 주면 실제 줄 번호가 왼쪽에 붙는다), `console(text, title)`(Raw에 `dim`/`ok`/`warn`/`err` span), `tree(text)`(줄 끝 ` +` = 새 파일, `  #` 뒤 = 설명), `flow(items, caption)`, `layers(rows, caption)`, `iface(name, members, stereotype, note)` + `grid(items, cols)`, `roadmap`, `steps`, `checklist`, `exgroup`, `qlist`, `answers`, `glossary_chapter`, `st(kind)`, `keep(...)`, `pagebreak()`.
    - 쪽 나눔: 표지는 1쪽(쪽 번호 없음). 장은 기본으로 이어 흐르고, 새 쪽에서 시작할 장만 `pb=True` (구현 미션, 질문, 해설은 새 쪽).
4. 빌드 (저장소 루트에서):
   `Docs\Handouts\.venv\Scripts\python.exe -I Docs\Handouts\src\lesson_1_5.py`
   출력의 `issues`가 빈 목록이어야 한다. 잡히는 것: 코드 블록의 한글, 104자를 넘는 코드 줄(줄 번호를 붙이면 7자를 더 센다), 28줄을 넘는 코드 블록(완성본이 들어갔다는 신호, `tag="now"`는 예외).
5. 검수 — 반드시 눈으로 본다.
   `Docs\Handouts\.venv\Scripts\python.exe -I Docs\Handouts\_engine\sheet.py <pdf> Docs\Handouts\_build <접두사>`로 접촉 인화(6쪽씩)를 만들어 Read로 전부 보고, 글자·코드·표는 `--page N`으로 확대해서 본다. 자주 나오는 문제와 해법:
    - 표지가 2쪽으로 넘침 → 정보 표 6행 이하, 목차 14개 이하, note 2〜3줄.
    - 장 끝의 상자 하나만 다음 쪽으로 넘어감 → 문장을 줄이거나, 상자를 빼고 그 내용을 다른 장의 문단으로 옮긴다.
    - 표의 첫 줄만 쪽 끝에 남거나 표가 쪽 사이에서 갈림 → 그 앞에 `pagebreak()`.
    - 긴 표가 한두 줄 넘침 → `compact=True`, 그래도 넘치면 줄이 접히는 칸의 폭(%)을 넓힌다.
    - `flow()` 칩이 두 줄로 접힘 → 칩은 7개 이하, 제목은 짧게.
    - 긴 경로·식별자가 좁은 칸에서 어색하게 끊김 → 칸 폭(%)을 넓힌다.
    - 코드가 오른쪽에서 잘림 → 줄을 나눈다 (가로 스크롤이 없다).
    - `hl=[…]`의 줄 번호는 `code()`에 넘긴 문자열의 1번 줄부터 센다. `start=`를 줬으면 실제 줄 번호로 센다.
    - `flow()` 칩의 작은 글씨에 긴 인라인 코드를 넣으면 글자 중간에서 끊긴다 → 칩에는 짧은 말만 쓰고 함수 이름은 캡션에 적는다.
    - 줄 범위를 `` `파일:12`〜`:26` ``처럼 붙여 쓰면 좁은 칸에서 숫자 중간이 끊긴다 → `〜` 양옆에 공백을 둔다. 강 번호 범위도 "1-1 〜 1-3강"처럼 띄운다.
    - 장마다 `pb=True`를 주면 반쯤 빈 쪽이 생긴다 → 개념 장은 이어 흐르게 둔다.
    - 고친 뒤 다시 빌드해 접촉 인화로 한 번 더 확인한다.
6. 강이 추가되거나 제목·시간이 바뀌었으면 계획서도 버전을 올려 다시 빌드한다. 강의 자료가 새로 나온 것만으로는 계획서를 건드리지 않는다 (계획서에는 진행 상황이 없다).
7. PDF 경로를 알려 주고, 이 강에서 Claud가 정해야 할 것(`box("decide")`에 넣은 것)을 채팅에 한 번 더 적는다.

## 계획서를 고칠 때

- 계획서는 스터디를 처음 시작할 때 보는 지침서다. 강의 전체를 1-1강부터 보여 준다. **진행 상황을 넣지 않는다**: 현재 위치, 완료·진행 중 표시, 지금 코드의 진단, 강의 자료 목록, 예전 계획과 달라진 점, 변경 이력 모두 넣지 않는다. Claud가 2026-11-14에 "전체 계획서에 지금까지 한 내용은 넣지 마. 처음 이 스터디를 할 때 볼 지침서 같은 거니까"라고 했다. (이미 코드가 있는 1-1 〜 1-3강을 계획서에 보통 강으로 넣은 것은 이 말에 대한 내 해석이다. Claud가 다르게 말하면 그쪽을 따른다.)
- 1장 "전체 한눈에 보기"(로드맵 + Part별 요약 + 전 강 목록)가 표지 바로 뒤 두 쪽에 온다. 특정 강이나 Part를 강조하지 않는다. 한 강을 강조하면 그 강의 자료처럼 읽힌다 (Claud가 첫 판을 "Logger 파트 같다"고 했다, 2026-11-14).
- 진행 상황이나 지금 코드의 문제를 Claud가 물으면 채팅으로 답한다. 문서로 원하면 계획서와 별개의 문서로 만든다.
- 강의 추가·삭제·순서 변경·시간 수정은 `curriculum.py`만 고친다. 계획서의 표, 합계, 로드맵 막대, 속도 표, 1장의 전 강 목록은 여기서 계산된다. Part 설명과 본문 속 "N-M강" 참조는 `plan.py`에 손으로 적혀 있으니 같이 고친다.
- 장을 옮기거나 더하면 본문 속 "N장", "N.M절" 참조와 표지의 읽는 법을 같이 고친다.
- 순서를 바꾸는 결정은 Claud가 한다. 바꾸자고 제안할 수는 있지만 계획서에 먼저 반영하지 않는다.
- Part 6〜8(DX11·DX12·Vulkan)은 5-4강 뒤에 상세화한다. 그 전에는 개요만 유지한다.

## 엔진을 고칠 때

- `common.py`나 `base.css`를 고쳤으면 `gallery.py`를 다시 빌드해 깨지지 않는지 본다. 이미 건넨 PDF는 그 때문에 다시 빌드하지 않는다 (다시 빌드하려면 버전을 올린다).
- 새 부품을 만들면 `gallery.py`에 견본을 추가하고 이 문서의 헬퍼 목록에 적는다.
- Pygments의 토큰 클래스(`.k`, `.s`, `.c`, `.ch` …)와 겹치는 CSS 클래스 이름을 `.code` 안에 만들지 않는다.
